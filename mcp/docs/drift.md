# The drift control: what a fact is called, and how to read a move

This repository owns no data, so the drift it can see is the drift only it can
see: an answer moving because the corpus or the library moved underneath it.
`python -m itl_mcp.drift` compares the answers the README promises with the ones
the checkouts give now, and when one has moved it prints which fact moved, what
it was, what it is, and what a move of that fact implies.

An assertion says *that* a claim broke. This says *which* answer moved and *why*
that matters, because a verdict flipping and a page's bytes shifting want
different repairs.

## The name of a fact

Every recorded fact is a question and the part of the answer it holds, written as
one string:

    <tool>(<arguments>).<field>

For example `as_modified_verdict(treaty_id='uk-us-2001').verdict`, or
`read_treaty_page(page=1, treaty_id='no-uk-2013').declared_sha256`. The question
is written exactly as `itl_mcp.drift.QUESTIONS` names it, so every fact answers a
question a reader can ask too.

Four parts of the verdict are not single fields but lists of sentences, and each
sentence is recorded under the **species** the verdict declares for it where it
is written:

    <tool>(<arguments>).<family>[<species>]

* `silences[...]` — what the data cannot say, each by the kind of limit it is
  (`compatibility_clauses_not_held`, `no_position_document`, …);
* `reasoning[...]` — the steps the verdict was reached by, each by the kind and
  subject it holds (`mli_standing[<party>]`, `verdict`, `chain_summary`,
  `covered_agreement[<party>]`, …);
* `assumptions[...]` — the rules imported from outside the data
  (`mli_in_force_for_both_parties`);
* `constructed_links[...]` — the joins this server built because no key exists
  (`covered_agreement[<filer>]`).

The species is stable across runs, and why it is a species and not a position is
that a reworded or reordered sentence then moves **one** named fact instead of
shifting every later index. A family whose species was empty, or shared by two
sentences, would lose one silently — so a test refuses both.

## How to read a move

A run that is not clean prints one block per moved fact:

    as_modified_verdict(treaty_id='uk-us-2001').verdict
        was: 'not-modified'
        now: 'modified'
        that means: the verdict moved. It is decided from the parties' MLI
        standing and the covered-agreement lookups, so one of those moved: ...

The `that means` sentence is not written per run. It is declared per fact in
`itl_mcp/drift.py` (`MEANING`), because two facts that moved want two different
sentences. A fact is matched to the **sharpest** prefix that occurs in its name:
the prefix appearing latest in the name wins, and a tie goes to the longer one,
so `.mli_articles.count` is explained by its own line rather than by
`.mli_articles[`. A fact with no field of its own keeps its tool's explanation.

## What is chosen to record

The substance of a promised answer, not every field. A count is kept beside the
sentences it counts, but a fixture that recorded every field would turn every
legitimate upstream addition into a red run and stop being read. So a treaty's
parties and pages are recorded and its prose title is not; checks are counted by
kind and by result rather than one fact per file; and a treaty appearing upstream
is a fact appearing, which is a different event from a value moving.

## The commands

    python -m itl_mcp.drift            # compare; non-zero when anything moved
    python -m itl_mcp.drift --write    # record the answers the checkouts give now
    python -m itl_mcp.status --write   # regenerate the board

`fixtures/expected-answers.json` is generated by `--write` and never edited by
hand: a value somebody typed can only ever be compared with what somebody typed,
and stops being a check the moment it is copied. Recording is a decision taken
after reading a move, not a way to make a red run green. `docs/status.md` is
generated the same way.

## One reading, taken twice

Every recorded answer is read by the tool and by the control through the **same
function** — `library.listing`, `library.page`, `verdict.status`,
`verdict.as_modified`, `editions.compare`, `reservations.scope`,
`verify.sources` — and so is every **refusal**, which is an answer too:
`verdict.refusal`, `editions.uncomparable`, `reservations.refusal` and
`reservations.unverifiable`. A control that re-derived a payload its own way
would be checking itself, and the day the tool stopped reading a field the
recorded fact would go on agreeing with an answer nobody returns.

A test compares the tool's payload with the control's for **every question and
every refusal**. The refusals have to be named in it rather than recorded,
because no recorded question reaches one: before this, all three tools'
refusals had drifted — the control returned a verdict refusal without the tool's
note, an edition refusal with an `article` key the tool never returns, and a
reservation refusal without its note. The one thing the test drops is
`sources()`'s two checkout paths, which are where this process read from and are
never committed.
